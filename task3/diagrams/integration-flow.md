# Integration Flow

## Сценарий: поступающий стал студентом

```text
Сотрудник
   │
   │ меняет статус поступающего
   ▼
Bitrix24
   │
   │ 1. Изменение статуса
   │ 2. Создание события в Outbox
   ▼
Outbox
   │
   │ событие StudentCreated
   ▼
Integration Service
   │
   ├───────────────────────────────┐
   │                               │
   │ API                           │ API
   ▼                               ▼
Moodle                         Student Cabinet
   │                               │
   │ create/update user            │ create/update profile
   │                               │
   ▼                               ▼
Учебная группа                 Профиль студента
   │
   ▼
Результат операции
   │
   ▼
Integration Service
   │
   ├── Moodle: success
   └── Cabinet: success
```

## Подробная последовательность

### 1. Изменение статуса

Сотрудник переводит поступающего в Bitrix24 в статус `Студент`.

Bitrix24 сохраняет изменение.

### 2. Создание события

В рамках той же транзакции создаётся запись в Outbox:

```json
{
    "event_id": "evt-123456",
    "event_type": "student.created",
    "student_id": "10025"
}
```

После фиксации транзакции событие гарантированно сохранено.

### 3. Обработка события

Integration Service получает событие и создаёт задачи для внешних систем:

```text
Moodle
Student Cabinet
```

### 4. Создание пользователя в Moodle

Integration Service вызывает API Moodle.

Перед созданием выполняется проверка по `external_student_id`.

Если пользователь уже существует, выполняется обновление.

Если пользователя нет — создаётся новый.

### 5. Добавление в учебную группу

После успешного создания/обновления пользователя выполняется операция добавления в соответствующую учебную группу.

Операция также должна быть идемпотентной.

### 6. Создание профиля в личном кабинете

Integration Service передаёт данные студента в API личного кабинета.

Личный кабинет создаёт или обновляет профиль.

### 7. Завершение

После успешного выполнения операций Integration Service сохраняет результат:

```text
Moodle  → success
Cabinet → success
```

Событие помечается как обработанное.

## Сценарий недоступности Moodle

Если Moodle недоступна:

```text
Bitrix24
   │
   ▼
Outbox
   │
   ▼
Integration Service
   │
   ├────── X Moodle
   │
   │ connection timeout
   ▼
retry queue
```

Событие остаётся в очереди.

После восстановления Moodle:

```text
retry queue
    │
    ▼
Integration Service
    │
    ▼
Moodle
    │
    ├── create/update user
    └── add to group
    │
    ▼
success
```

## Сценарий повторной доставки

Если одно событие пришло дважды:

```text
event_id = evt-123456
```

Integration Service проверяет наличие этого `event_id`.

Если событие уже успешно обработано:

```text
event_id = evt-123456
status = success
```

повторная бизнес-операция не выполняется.

Дополнительной защитой является уникальный внешний идентификатор студента в целевой системе.

## Сценарий частичного отказа

Если Moodle успешно обработала студента, а личный кабинет вернул ошибку:

```text
Moodle  → success
Cabinet → failed
```

при повторной обработке Moodle не создаётся повторно.

Повторяется только операция для личного кабинета.

## Reconciliation

Периодическая проверка сравнивает:

```text
Bitrix24 students
        │
        ├──── Moodle
        │
        └──── Student Cabinet
```

Если студент отсутствует в одной из систем, создаётся задача на повторную синхронизацию.
