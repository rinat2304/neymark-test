# Задание 3 — Интеграция Bitrix24, Moodle и личного кабинета

## Задача

Спроектировать взаимодействие следующих систем:

* Bitrix24 On-Premise;
* CRM для работы с поступающими;
* корпоративный портал / КЭДО / бизнес-процессы;
* Moodle 5.2;
* личный кабинет студента.

Все системы размещаются on-premise на виртуальных машинах.

Ориентировочная нагрузка:

* до 350 активных студентов;
* до 100 новых лидов в пиковый период;
* до 150 сотрудников.

## Основной сценарий

Когда сотрудник переводит поступающего в Bitrix24 в статус студента:

1. Bitrix24 фиксирует изменение статуса.
2. Создаётся событие о необходимости создать/активировать студента во внешних системах.
3. Событие передаётся в интеграционный слой.
4. Интеграционный слой создаёт или обновляет учётную запись студента в Moodle.
5. Студент добавляется в необходимые учебные группы.
6. Создаётся или активируется учётная запись в личном кабинете.
7. Результат операции фиксируется для возможности повторной обработки.

## Принцип владения данными

Bitrix24 является источником истины для данных о поступающем и его статусе.

Moodle отвечает за:

* учебные курсы;
* учебные группы;
* прохождение обучения;
* оценки и другие данные обучения.

Личный кабинет отвечает за пользовательское представление данных студента и функции, относящиеся непосредственно к кабинету.

Внешние системы не должны изменять статус поступающего/студента непосредственно в базе Bitrix24.

## Принцип интеграции

Интеграция выполняется через API и асинхронную доставку событий.

Прямой доступ одной системы к базе данных другой системы не используется.

Это снижает связанность систем и не привязывает интеграцию к внутренней структуре БД конкретного продукта.

## Надёжность

Для событий используется паттерн Outbox.

Событие сначала сохраняется локально вместе с изменением состояния в Bitrix24, после чего отдельный обработчик доставляет его во внешние системы.

Для каждой операции используется стабильный идентификатор события/студента, позволяющий безопасно повторять обработку.

При временной недоступности Moodle событие не теряется и остаётся в очереди на повторную обработку.

## Идемпотентность

Повторная доставка одного события не должна создавать второго пользователя.

Для этого внешние системы используют внешний идентификатор студента, полученный из Bitrix24.

Операции создания пользователя и добавления в группу должны быть идемпотентными.

## Контроль рассинхронизации

Периодическая reconciliation-задача сравнивает студентов в Bitrix24 с состоянием во внешних системах.

Она выявляет:

* события, которые не были обработаны;
* операции со статусом ошибки;
* студентов, отсутствующих в Moodle;
* студентов, отсутствующих в личном кабинете.

После обнаружения расхождения операция помещается на повторную обработку.

Подробная схема и API-контракт находятся в остальных файлах каталога `task3`.
