# Архитектура интеграции

## 1. Общая схема

```text
                         ┌─────────────────────┐
                         │      Bitrix24       │
                         │  Источник данных    │
                         │  о поступающих       │
                         └──────────┬──────────┘
                                    │
                           событие "студент"
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │   Integration       │
                         │      Service        │
                         │                     │
                         │ Outbox / Queue      │
                         │ Retry               │
                         │ Idempotency         │
                         │ Reconciliation      │
                         └───────┬─────┬───────┘
                                 │     │
                       REST/API   │     │   REST/API
                                 │     │
                    ┌────────────┘     └─────────────┐
                    ▼                                ▼
           ┌─────────────────┐              ┌─────────────────┐
           │    Moodle 5.2   │              │ Student Cabinet │
           │                 │              │                 │
           │ Users           │              │ Student profile │
           │ Groups          │              │ Personal data   │
           │ Courses         │              │ Status          │
           └─────────────────┘              └─────────────────┘
```

## 2. Ответственность систем

### Bitrix24

Bitrix24 является источником истины для:

* идентификатора поступающего/студента;
* ФИО и основных персональных данных;
* статуса поступающего;
* факта зачисления.

Изменение статуса выполняется в Bitrix24.

### Integration Service

Интеграционный сервис отвечает за:

* получение событий;
* хранение необработанных событий;
* доставку событий во внешние системы;
* повторные попытки;
* идемпотентность;
* журналирование результата;
* обнаружение рассинхронизации.

### Moodle

Moodle является источником истины для учебных данных:

* курсов;
* учебных групп;
* зачисления на курсы;
* результатов обучения.

### Личный кабинет

Личный кабинет предоставляет студенту интерфейс для работы со своими данными и функциями системы.

При этом источник основных данных о статусе студента остаётся Bitrix24.

---

## 3. Передача данных

Предлагается использовать асинхронную передачу событий.

При изменении статуса в Bitrix24 создаётся событие:

```text
StudentStatusChanged
```

Пример:

```json
{
    "event_id": "evt-123456",
    "student_id": "student-10025",
    "event_type": "student.created",
    "occurred_at": "2026-09-18T10:15:00Z"
}
```

Интеграционный сервис получает событие и выполняет необходимые операции:

```text
Bitrix24
   │
   │ StudentStatusChanged
   ▼
Outbox
   │
   ▼
Integration Service
   │
   ├──────────────► Moodle
   │
   └──────────────► Student Cabinet
```

---

## 4. Почему не использовать прямой доступ к БД

Не рекомендуется делать:

```text
Bitrix24 DB ─────────► Moodle DB
```

или:

```text
Bitrix24 DB ─────────► Cabinet DB
```

Причины:

* сильная связанность систем;
* зависимость от внутренней структуры БД;
* риск нарушения внутренних ограничений продукта;
* сложность обновления Bitrix24 или Moodle;
* отсутствие нормального контроля повторной доставки;
* сложность обработки временной недоступности системы.

Предпочтительный вариант:

```text
Bitrix24 → API/Event → Integration Service → API → Moodle
                                           └────→ Cabinet
```

---

## 5. Outbox

Чтобы событие не потерялось при сбое, его необходимо сохранить до отправки во внешнюю систему.

Упрощённо:

```text
1. Изменить статус студента
2. Сохранить событие в Outbox
3. Зафиксировать транзакцию
4. Отдельный worker получает событие
5. Отправить его во внешнюю систему
6. Сохранить результат
```

Если внешний сервис недоступен, событие остаётся в Outbox.

Например:

```text
event_id     status       attempts
evt-001      pending      0
evt-002      sent         1
evt-003      failed       5
```

---

## 6. Moodle недоступна 6 часов

Предположим:

```text
10:00 — студент зачислен
10:01 — Moodle становится недоступна
16:00 — Moodle снова доступна
```

Событие не удаляется после первой неудачной попытки.

Worker выполняет повторные попытки:

```text
10:01 → ошибка
10:02 → ошибка
10:04 → ошибка
10:08 → ошибка
...
```

Для повторных попыток используется exponential backoff с ограничением максимального интервала.

После восстановления Moodle:

```text
Moodle доступна
       │
       ▼
очередь содержит pending/failed события
       │
       ▼
повторная обработка
       │
       ▼
создание пользователя
       │
       ▼
добавление в учебную группу
       │
       ▼
event = processed
```

Таким образом, шестичасовой простой Moodle не приводит к потере события.

---

## 7. Защита от дубликатов

Основной идентификатор студента должен быть стабильным и единым между системами.

Например:

```text
Bitrix student_id = 10025
```

В Moodle хранится соответствующий внешний идентификатор:

```text
external_student_id = 10025
```

При повторной обработке:

```text
student_id = 10025
```

сервис сначала проверяет существующую запись.

Если пользователь уже существует:

```text
создавать второго пользователя не нужно
```

а выполняется операция обновления/проверки.

Для событий используется уникальный `event_id`.

Это защищает от повторной обработки одного и того же события.

---

## 8. Обнаружение пропущенных записей

Одной очереди недостаточно, поэтому нужен периодический reconciliation job.

Например, раз в час:

```text
Bitrix24
   │
   │ список студентов
   ▼
Reconciliation
   │
   ├── студент есть в Moodle       → OK
   ├── студента нет в Moodle       → создать/повторить
   ├── операция pending            → повторить
   └── операция failed             → повторить
```

Аналогичная проверка выполняется для личного кабинета.

Таким образом, система может восстановиться даже в случае, если событие было потеряно из-за ошибки интеграционного сервиса.

---

## 9. Статусы интеграционной операции

Для каждой операции можно использовать состояния:

```text
pending
processing
success
failed
```

Пример:

```text
student_id: 10025
system: moodle
status: failed
attempts: 4
last_error: connection timeout
next_retry_at: 2026-09-18 16:30:00
```

После успешной обработки:

```text
status = success
```

---

## 10. Что происходит при частичном успехе

Например:

```text
Bitrix24 → OK
Moodle → OK
Student Cabinet → ERROR
```

Это не должно приводить к повторному созданию пользователя в Moodle.

Для каждой внешней системы состояние отслеживается отдельно:

```text
student_id | system  | status
-----------|---------|--------
10025      | moodle  | success
10025      | cabinet | failed
```

При повторной обработке выполняется только незавершённая операция.

---

## 11. Масштабирование

Для заданной нагрузки отдельный интеграционный сервис с одним или несколькими worker-процессами будет достаточен.

Исходные объёмы:

* 350 активных студентов;
* до 100 новых лидов в пиковый период;
* до 150 сотрудников.

Высокая пропускная способность здесь не является основной проблемой. Основные требования к интеграции — надёжность, отсутствие потери событий, идемпотентность и возможность восстановления после отказов.

При дальнейшем росте нагрузки worker'ы можно масштабировать горизонтально.

---

## 12. Восстановление после отказа

При перезапуске Integration Service:

1. незавершённые операции остаются в хранилище;
2. worker снова выбирает `pending`/`failed` записи;
3. выполняется повторная доставка;
4. идемпотентность предотвращает создание дублей;
5. reconciliation дополнительно проверяет конечное состояние систем.

Таким образом, система не зависит от того, был ли Integration Service перезапущен во время обработки события.
