# API Events

## 1. Событие создания студента

При переводе поступающего в статус студента Bitrix24 создаёт событие:

```text
student.created
```

Пример:

```json
{
    "event_id": "evt-123456",
    "event_type": "student.created",
    "occurred_at": "2026-09-18T10:15:00Z",
    "student": {
        "id": "10025",
        "external_id": "10025",
        "first_name": "Иван",
        "last_name": "Иванов",
        "middle_name": "Иванович",
        "email": "ivanov@example.local"
    }
}
```

## 2. Идентификаторы

`event_id` — уникальный идентификатор события.

Он используется для защиты от повторной обработки одного и того же события.

`student.id` — стабильный идентификатор студента в Bitrix24.

Он используется как внешний идентификатор во внешних системах.

Например:

```text
Bitrix24 student.id
        │
        ├── Moodle external_student_id
        │
        └── Cabinet external_student_id
```

## 3. Создание/обновление пользователя в Moodle

Integration Service обращается к API Moodle.

Логика:

```text
найти пользователя по external_student_id
        │
        ├── найден → обновить данные
        │
        └── не найден → создать
```

После этого выполняется добавление пользователя в необходимую учебную группу.

Операция должна быть идемпотентной.

## 4. Создание/обновление профиля в личном кабинете

Integration Service передаёт:

```json
{
    "external_student_id": "10025",
    "first_name": "Иван",
    "last_name": "Иванов",
    "middle_name": "Иванович",
    "email": "ivanov@example.local"
}
```

Если профиль уже существует, выполняется обновление.

Если профиля нет — создаётся новый.

## 5. Ответ внешней системы

Успешный ответ должен содержать идентификатор созданного или найденного объекта:

```json
{
    "status": "success",
    "external_id": "10025",
    "system_id": "moodle-user-501"
}
```

При ошибке:

```json
{
    "status": "error",
    "error_code": "TEMPORARY_UNAVAILABLE",
    "message": "Service unavailable"
}
```

## 6. Повторные попытки

Временные ошибки должны приводить к повторной попытке:

* HTTP timeout;
* HTTP 502;
* HTTP 503;
* HTTP 504;
* временная ошибка подключения к БД.

Ошибки данных не следует бесконечно повторять.

Например:

```text
400 invalid email
422 invalid group
```

Такие ошибки переводятся в `failed` и требуют исправления данных или ручного вмешательства.

## 7. Idempotency

Для запросов, создающих ресурс, используется идемпотентный ключ:

```text
Idempotency-Key: student-10025
```

или комбинация:

```text
event_id + operation
```

Например:

```text
evt-123456:create-moodle-user
```

Повтор того же запроса не должен создать второго пользователя.

## 8. Таймауты

Для внешних API устанавливается ограниченный timeout.

Например:

```text
connect timeout: 3 sec
read timeout: 10 sec
```

Конкретные значения должны быть уточнены после нагрузочного тестирования.

Нельзя оставлять HTTP-запрос без ограничения времени ожидания.

## 9. Логирование

Для каждой операции необходимо сохранять:

```text
event_id
student_id
system
operation
attempt
status
created_at
processed_at
error
```

Пример:

```text
evt-123456
10025
moodle
create_user
3
success
2026-09-18 16:12:05
```

Это позволяет найти конкретную ошибку и повторить обработку.

## 10. Безопасность

Интеграционные API должны быть доступны только внутри защищённой инфраструктуры.

Для авторизации могут использоваться:

* service account;
* API token;
* mTLS.

Секреты не должны храниться в исходном коде.

Они должны передаваться через защищённое хранилище секретов или переменные окружения.

## 11. Принцип контракта

Integration Service не должен зависеть от внутренней структуры БД Bitrix24 или Moodle.

Он работает с определённым API-контрактом:

```text
Bitrix24
    │
    │ event contract
    ▼
Integration Service
    │
    ├── Moodle API contract
    │
    └── Cabinet API contract
```

Это позволяет независимо изменять внутреннюю реализацию каждой системы без изменения всей интеграционной архитектуры.
